# 第5回 解答

## 演習
- 回答モデル（実行時の[model]）：`gemini-3.5-flash-lite`
- 比較した質問：`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`
- 対象資料（全文投入と他の方式で範囲が違う点も記録）：
  - 講座資料（PDFページ単位で分割された第1回〜第3回の講義スライド資料）。
  - **範囲の違い**：`全文投入`（`--full-context`）は対象資料の全テキスト（227,971文字）を一度にプロンプトへ入力する。一方、`ベクトル検索`・`Tree`・`Graph` はツール呼び出しによって質問に関連する一部のページ本文のみを取得して入力する。

### 各方式の結果
| 方式 | 回答の要点・正しさ | 引用ページと根拠 | 時間（秒） | 入力／出力トークン数 | モデル応答回数 | 生成API推定費用（USD） |
|---|---|---|---|---|---|---|
| 全文投入 | △（要点を直接答えず、資料を見て自分でまとめるよう促すヒント形式の応答になった） | 第2回・PDF p.51, 52（資料の場所のみ提示） | 2.08 | 117,025 / 217 | 1 | $0.004694 |
| ベクトル検索 | ○（元の重みを固定し低ランク行列の差分のみ学習するLoRAと、元の重みを4bit量子化するQLoRAを正確に説明） | 第2回・PDF p.51, 52 | 2.84 | 3,027 / 203 | 2 | $0.001416 |
| Tree | ○（元の重みWを固定し低ランク行列A・Bを学習するLoRAと、4bit量子化を加えるQLoRAを正確に説明） | 第2回・PDF p.52 | 5.64 | 9,214 / 324 | 5 | $0.003574 |
| Graph | ○（モデル本体の重み固定・低ランク差分学習のLoRAと、4bit圧縮を加えるQLoRAを正確に説明） | 第2回・PDF p.51, 52 | 8.98 | 5,771 / 199 | 2 | $0.002229 |

- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行したところ、上位5件として第2回「基盤モデルの仕組み」の **p.52、p.51、p.60、p.47、p.61** が返された。
  - 最上位の **p.52**（「LoRA と QLoRA ：大きなモデルも GPU 1 台で調整できる」）および **p.51**（「PEFT ：モデル全体ではなく、一部だけを学習する」）の本文において、「元の重み W は固定して学習せず、小さな低ランク行列 A・B（差分）だけを学習すること（LoRA）」および「さらに元の重みを 4bit に圧縮すること（QLoRA）」が明記されていることを確認できた。
- --traceで見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - **全文投入**：ツール呼び出しなし（0回）。
  - **ベクトル検索**：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を **1回** 呼び出し、上位5ページを取得。
  - **Tree**：`browse_tree` を計 **4回** 呼び出し、以下の階層順に目次をたどって本文を取得した。
    1. `browse_tree({})`（講義一覧を取得）
    2. `browse_tree({'node_id': 'lec02-main'})`（第2回「基盤モデルの仕組み」の章一覧を取得）
    3. `browse_tree({'node_id': 'lec02-main-s045'})`（章「選んだモデルを、いつ・どう直すか」のページ一覧と先頭文を取得）
    4. `browse_tree({'node_id': 'lec02-main-p052'})`（末端ページ p.52 の全文717文字を取得）
  - **Graph**：`search_graph({'query': 'LoRA QLoRA 固定 学習'})` を **1回** 呼び出し、入口ページ（seeds: `lec02-main-p052` 等）とグラフ上の隣接・共通語ページ（expanded）の全文をまとめて取得。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - **取得できたのに回答へ使えなかった例**：`全文投入` では資料全体（p.51, 52 を含む全ページ）が入力に含まれていたにもかかわらず、大量のコンテキストの影響か、学習支援用のヒント誘導ルールが強く働き、直接的な回答ではなく「資料を参照してまとめてみてください」という応答になってしまった。また、ベクトル検索の p.60・p.47・p.61 や Graph で拡張された周辺ページも、今回の単一ページで完結する質問の回答には直接使われなかった。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **採用したい方式**：**ベクトル検索（RAG）**。
  - **理由**：単一ページに根拠がまとまっている質問に対して、最も少ないトークン数（3,027 tokens）と最安のAPIコスト（$0.001416）で、正確かつ根拠ページ付きの回答を生成できたため。
  - **比較条件の限界**：今回は「第2回 p.52」の1ページのみで根拠が完結する単一ページ質問で比較したため、ベクトル検索が最も優位になった。複数ページや章をまたぐ比較質問、あるいは検索語と本文の表現が大きく異なる質問では、単純なベクトル検索では取りこぼしが起きる可能性があり、Tree や Graph の方が有効になる余地がある。
- 気づき・疑問：
  - 全文投入は「コンテキストに入りさえすれば必ず正確に答えてくれる」わけではなく、入力トークンが11万を超えるとコストが跳ね上がるうえに指示の効き方が不安定になることがあると分かった。
  - Tree 方式はベクトル検索を使わずに人間が目次をめくるように正確に p.52 へたどり着ける点が興味深かったが、階層を1段ずつ降りるたびにモデル応答（5回）が発生するため、トークン数と応答時間が増加するトレードオフがある。

## 宿題
- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の `RAG_TOP_K` の値をデフォルトの `5` から `3` に変更し、ベクトル検索でモデルに渡す上位ページ数を削減した。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - **比較した質問**：`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`
  - **固定した条件**：使用モデル（`gemini-3.5-flash-lite`）、対象資料（講義PDFデータベース）、実行モード（通常のベクトル検索 `--trace`）。
- 結果（変更前後の回答・根拠、--traceの出力、時間・トークン数・生成API推定費用など）：
  - **変更前（`RAG_TOP_K = 5`）**：
    - 回答・根拠：LoRA（元の重みを固定し低ランク行列の差分を学習）とQLoRA（元の重みを4bitに圧縮）を正確に回答。引用は `第2回・PDF p.51, 52`。
    - `--trace` 出力：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し。
    - 負荷指標：時間 `2.84 秒` / 入力 `3,027 tokens`・出力 `203 tokens`（応答 2回） / 推定費用 `$0.001416 USD`。
  - **変更後（`RAG_TOP_K = 3`）**：
    - 回答・根拠：変更前と同様に LoRA と QLoRA の仕組みを過不足なく正確に回答。引用も `第2回・PDF p.51, 52` を維持。
    - `--trace` 出力：`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を1回呼び出し（上位3件のみ取得）。
    - 負荷指標：時間 `2.93 秒` / 入力 `2,079 tokens`・出力 `162 tokens`（応答 2回） / 推定費用 `$0.001029 USD`。
- 改善した例と、残る失敗・制約：
  - **改善した点**：上位3件の中に正解の根拠ページ（p.52, p.51）が含まれていたため、回答の正確性と引用根拠を一切損なうことなく、**入力トークン数を約31%削減（3,027 → 2,079 tokens）し、生成API推定費用も約27%削減（$0.001416 → $0.001029）**することができた。
  - **残る失敗・制約**：今回は1〜2ページに根拠が集中する質問だったため `TOP_K = 3` でも問題なかったが、複数の章や回にまたがる横断的な質問に対しては、取得件数を3件に絞ることで必要な根拠ページが上位から漏れる（検索の再現率が下がる）リスクが残る。
- 気づき・疑問：
  - `RAG_TOP_K` を減らすことでノイズとなる無関係なページ（第2回 p.60 や p.61 など）がプロンプトから除外され、コスト削減だけでなくコンテキストの純度向上にもつながることが確認できた。実運用では質問の複雑さに応じて `TOP_K` やリランキングを組み合わせる設計が重要だと感じた。
